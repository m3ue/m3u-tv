# Platform Release Matrix

This document is the production release source of truth for the Flutter client. It records the toolchain baseline, signing placeholders, and current blockers without claiming platform builds pass before the matching SDKs and native dependencies are present. Blocking release targets: Linux desktop, Windows desktop, Android phone/tablet, and Android TV. macOS, iOS, iPadOS, and tvOS are non-blocking gated tracks for this Desktop+Android release.

## Active CI Baseline

The CI gate workflow is `.github/workflows/ci.yml`. It runs these Flutter gates from `flutter_client/` with the pinned Flutter binary:

```bash
/tmp/flutter/bin/flutter analyze
/tmp/flutter/bin/flutter test
```

The release publication workflow is `.github/workflows/release.yml`. It builds and publishes artifacts for all platforms (Android, Linux, Windows, iOS, tvOS, macOS) with separate non-Apple and Apple release tracks.

The workflow does not run Electron builder commands, Electron scripts, or React Native/Expo release jobs. The React Native/Expo app has been fully removed; only the Flutter client remains in this repository.

## Honest Release Blockers

- Android SDK/JDK setup, signed release artifacts, Play Console metadata, physical Android phone/tablet QA, and physical Android TV hardware validation are not completed by this baseline task. Emulator logs are supplemental only.
- **Android's playback backend order was reverted: Media3/ExoPlayer is primary again (`PlaybackCapabilities.forPlatform(android)` = `[androidExoPlayer, androidMpv, serverTranscode]`), with native mpv as the automatic fallback and m3u-editor server transcode as the final fallback, not the other way around.** mpv had briefly been made primary, but real-Shield-hardware testing under genuine HDR content hit two separate, confirmed Tegra GPU-driver bugs in mpv's rendering path in a row: `gpu-next`'s `samplerExternalOES`-in-both-shader-stages linker rejection under hardware decode (root-caused via Plezy's own Android mpv core, which names and works around this exact bug -- their `initialVideoOutput()` already only offers `gpu-next` for software-decode sessions, `gpu` for hardware-decode ones), and, after matching that fix, a second crash allocating an `rgba16f` HDR-precision framebuffer on `vo=gpu` itself. Checking Plezy's actual architecture (`plezy/android/app/src/main/kotlin/com/edde746/plezy/exoplayer/ExoPlayerPlugin.kt`) found `mpvCore` explicitly commented `// MPV fallback player` -- ExoPlayer is their primary Android path, mpv only a fallback for streams ExoPlayer can't handle, same as Plex/Nuvio/Stremio's approach of leaning on Android's native HDR-capable media pipeline (hardware tone-mapping via a properly-tagged `Surface`) rather than mpv's GPU-shader FBO tone-mapping, which is what exposes this Tegra driver's rough edges in the first place. This app's own `androidMpv` capability row was already labeled `displayName: 'Android MPV fallback'` even while briefly ordered first -- a leftover inconsistency from whenever the order was flipped, now corrected to match. The Android mpv core keeps its `vo=gpu` fix (`MpvPlayerCore.kt`) and its threading fix (`Dispatchers.IO.limitedParallelism(1)`, fixing real UI jank independent of the HDR crash) regardless, since mpv is still reachable as a fallback for streams ExoPlayer can't play (advanced codecs, advanced subtitle formats -- see `PlaybackCapabilities.androidExoPlayer`'s `false` flags for exactly those; external subtitles are now handled directly on the ExoPlayer path too, see below). Verified: `flutter analyze`/`flutter test` pass (239 tests across `test/playback`, `test/ui/player`, `test/integration`, including two tests updated for the new order -- `playback_adapter_contract_test.dart` and `playback_orchestrator_test.dart` both previously asserted mpv-first). Not yet verified: real-Shield-hardware confirmation that HDR playback via ExoPlayer avoids the crash entirely (expected, since ExoPlayer never exercises mpv's GPU-shader path for content it can already play) and that mpv fallback sessions (now carrying the `vo=gpu` fix) are stable for whatever content still needs them.
- **Real-Shield-hardware retest of the ExoPlayer-primary revert found ExoPlayer no longer crashes on HDR content (progress), but the picture renders solid red and playback is visibly jittery/stop-motion -- root-caused to `Media3PlaybackPlugin.kt` rendering into a Flutter `SurfaceProducer` texture instead of a real window-attached surface.** A Flutter `SurfaceProducer` is an offscreen GL texture Flutter's own compositor samples and redraws; it is never attached to a real `Display`, so SurfaceFlinger has no HDR dataspace to negotiate and the decoder's raw BT.2020/PQ pixel data gets sampled as plain BT.709/SDR -- a strong red/magenta push, not a subtle tint, exactly what was observed, and consistent with the heavier per-frame decode-to-texture-copy path also explaining the jitter. Checking Plezy's actual ExoPlayer implementation (`plezy/android/app/src/main/kotlin/com/edde746/plezy/exoplayer/ExoPlayerCore.kt`, `plezy/android/app/src/main/kotlin/com/edde746/plezy/shared/PlayerSurfaceHost.kt`) confirmed it renders into a real, window-attached `SurfaceView` (Hybrid Composition), not a Flutter texture. Fixed by porting that shape: a new `Media3PlatformView.kt`/`Media3PlatformViewFactory` (`m3u_tv/android_exo_view`, registered in `MainActivity.kt`) hosts a raw `SurfaceView` per `playerId`, mirroring the existing `MpvPlayerPlatformView.kt`/`AndroidMpvBackend` shape this app already uses for its mpv fallback; `Media3PlaybackPlugin.kt`'s `load` now calls `player.setVideoSurfaceView(surfaceView)` instead of creating a `SurfaceProducer`, waiting for the view via `waitForSurfaceView` (mirroring `MpvPlayerPlugin.kt`'s `waitForCore`) since the platform view is created asynchronously by Flutter and may not exist yet when `load` arrives. `AndroidPlaybackAdapter` now implements `PlatformViewProvider` instead of `VideoTextureProvider`; `lib/playback/native_video_surface.dart`'s existing Hybrid Composition plumbing (already used for the mpv platform view) and `PlaybackOrchestrator`'s generic `is PlatformViewProvider` checks required no changes. Verified: `flutter analyze`/`flutter test` pass. Real-Shield-hardware retest confirmed the red tint is gone and HDR10 dataspace switching works (confirmed switching into HDR10 and back to SDR on stop). Some stuttering remained, addressed in the next bullet.
- **After the `SurfaceView` fix above, real-Shield-hardware playback still showed some stuttering, and a fresh `Choreographer` capture during playback showed `Skipped 231 frames! The application may be doing too much work on its main thread.`** `Media3PlaybackPlugin.kt`'s `onMethodCall` had no `TaskQueue` configured, so it ran on Flutter's platform channel thread -- the Android main/UI thread -- and `load()` built a full `ExoPlayer` (`ExoPlayer.Builder(context).build()`) plus a `MediaSession` (`MediaSession.Builder(context, player).build()`, a binder call into the system `MediaSessionService`) synchronously there on every channel load, the same class of bug the Android mpv core already had and fixed (`MpvPlayerCore.kt`'s scope was `Dispatchers.Main` until this session). **First attempt at a fix regressed to a black screen and was reverted.** Tried moving all ExoPlayer creation/control to a dedicated `HandlerThread` via `ExoPlayer.Builder.setLooper(playbackThread.looper)` (mirroring the mpv threading fix), with `MethodChannel.Result`/`EventChannel.EventSink` calls hopping back to `mainHandler` -- this compiled and passed `flutter analyze`/`flutter test`, but real-Shield-hardware testing showed a black screen: HDR display-mode switching still fired (so frames were reaching SurfaceFlinger), but nothing rendered visibly. Something about moving ExoPlayer's application-thread Looper off main is not compatible with this app's `SurfaceView`/`MediaSession` attachment path in a way code review alone did not surface, so rather than guess again, this was reverted in full back to the known-working, main-thread-everything state (colors fixed, HDR confirmed, no black screen, only the stutter outstanding). The jank fix remains open, pending a correctly-targeted diagnosis backed by real evidence (a proper logcat capture during the stutter, not blind re-attempts) before the next try. Verified: `flutter analyze`/`flutter test` pass; `./gradlew :app:compileDebugKotlin` succeeds -- for the reverted (main-thread) state.
- **External subtitles were the one gap left in the Android platform-support matrix -- `AndroidPlaybackAdapter`/`Media3PlaybackPlugin.kt` never read `PlaybackSource.externalSubtitles` at all, only the mpv fallback path did, so a sideloaded `.srt`/`.vtt` silently disappeared for any stream ExoPlayer handled directly.** Fixed by threading `source.externalSubtitles` through `MethodChannelAndroidMedia3Host.load()` (mirroring the `mpv_native_backend_base.dart`/`desktop_libmpv_backend.dart` shape already used for the native mpv backends) into `Media3PlaybackPlugin.kt`'s `buildMediaItem`, which now builds a `MediaItem.SubtitleConfiguration` per sidecar file (mime-typed from the file extension -- `text/vtt`, `application/ttml+xml`, `text/x-ssa`, defaulting to `application/x-subrip`) and attaches them via `MediaItem.Builder.setSubtitleConfigurations`, in addition to whatever's embedded in the container; the HLS-format-mismatch retry path (`PlayerState.retryAsTs`) carries the same configurations forward so a mid-load fallback doesn't drop them. `PlaybackCapabilities.androidExoPlayer.supportsExternalSubtitles` flipped `false` -> `true` to match (this is basic-format support only -- SRT/VTT/TTML/SSA via ExoPlayer's built-in text renderers -- `supportsAdvancedSubtitleFormats` stays `false`, matching what mpv alone still covers). Verified: `flutter analyze lib test` and `flutter test` (997 tests, including `playback_adapter_contract_test.dart`'s capability-flag assertion updated to match) pass; `./gradlew :app:compileDebugKotlin` succeeds. Not yet verified: real-device confirmation that a sideloaded subtitle file actually renders correctly on the ExoPlayer path.
- **Genuine HDR (PQ) live channels reproducibly crashed the whole app on a real Shield Android TV -- root-caused (after three rounds of band-aid libplacebo tweaks that only ever delayed the crash to the next shader compile) to using `vo=gpu-next` for hardware-decoded video on Tegra, a combination Plezy's own Android mpv core deliberately avoids by name.** Each `logcat mpv:V DEBUG:V AndroidRuntime:E` capture showed the process simply vanishing mid-render -- no `AndroidRuntime` fatal exception, no `DEBUG` native tombstone -- with `hdr-compute-peak=no`, then `tone-mapping=clip`/`dither=no`, each only moving the crash later (past the first rendered frame, into subtitle/OSD init) rather than fixing it, which pointed away from any single libplacebo feature. Checking the vendored `dev.jdtech.mpv` binding fork (`edde746/libmpv-android`, pinned `v1.0.7`) for a missing upstream fix found a real, exact-match Tegra GPU-driver-crash issue upstream, but confirmed via `gh api` that its fix (`0eea8cc`, "throw Java exception instead of exit(1) on fatal errors") was already included -- not the cause, but confirmation this class of Tegra driver instability is real and known for this binding. The actual answer came from Plezy's own Android core (`plezy/android/app/src/main/kotlin/com/edde746/plezy/mpv/MpvPlayerCore.kt`), which picks its `vo` by decode path: `if (hardwareDecoding) "gpu" else "gpu-next,gpu"`, with a comment naming the exact mechanism -- gpu-next samples hardware-decoded frames as a `samplerExternalOES` that libplacebo declares in both shader stages, and the Tegra GLES linker rejects that pairing ("struct type mismatch between shaders for uniform"), documented in Plezy's own issue #2010 as a solid blue screen with audio on Shield (this app crashed outright instead, plausibly because HDR's extra shader permutations give the Tegra driver less chance to fail gracefully than Plezy's simpler repro). This app always hardware-decodes (`hwdec=mediacodec-copy`, no software-decode fallback path) and was using `vo=gpu-next,gpu` -- exactly the broken combination. Fixed by matching Plezy exactly: `vo=gpu` (mpv's older, non-libplacebo shader pipeline, which doesn't build the broken sampler pairing and still does its own HDR-to-SDR tone-mapping/color management) instead of `gpu-next,gpu`, and reverting the `hdr-compute-peak`/`tone-mapping`/`dither` band-aids from the three earlier rounds now that they're no longer needed (gpu-next's Dolby Vision RPU-reshaping advantage over `vo=gpu` doesn't even apply here either way -- FFmpeg's mediacodec wrapper exports no DOVI side data under hardware decode, so gpu-next couldn't reshape a hardware-decoded DV stream even without the crash). Verified: `./gradlew :app:compileDebugKotlin` succeeds. Not yet verified: whether this actually closes the crash on the real Shield hardware that reproduced all three earlier attempts -- needs the same real-device retest as everything else in this document, though this is now a root-cause fix backed by a named, documented Tegra driver incompatibility from a working reference implementation, not another speculative mitigation.
- **Separately, real Shield hardware also showed heavy UI jank ("Skipped N frames!", laggy loading spinners) unrelated to the HDR crash above and not explained by debug-over-WiFi (which only affects the log/debugger transport, never on-device main-thread scheduling).** Decompiling the `dev.jdtech.mpv` AAR showed its `suspend fun command()`/`setProperty()`/etc. are not real suspend functions -- they call their blocking native JNI counterpart directly on whatever thread invokes them, with no internal dispatcher hop anywhere in the bytecode. `MpvPlayerCore.kt`'s coroutine scope was `Dispatchers.Main`, meaning every mpv command/property/create/attach call -- including `loadfile`, which can block for several seconds opening a slow live stream -- executed directly on the Android UI thread, observed as up to ~3.8s of blocked main thread (`Choreographer: Skipped 231 frames!`). Fixed by moving `MpvPlayerCore`'s scope to `Dispatchers.IO.limitedParallelism(1)` (off the UI thread, but still single-threaded like Main was, since other fields in the class like `readyEmitted`/`lastLogText` rely on that single-threaded assumption without their own synchronization) and making `emit`/`emitError` hop to the main thread explicitly via a `Handler(Looper.getMainLooper())` only where actually required (Flutter channel calls). Verified: `./gradlew :app:compileDebugKotlin` succeeds. Not yet verified on real hardware.
- **Live UHD channels intermittently black-screened with "unrecognized file format" across multiple platforms (Windows, macOS, Android) -- root-caused to an upstream IPTV provider 503 on this specific UHD channel, not an app-side bug on any platform.** Real-hardware testing on a physical Shield Android TV (NVIDIA Shield, confirmed HDR-capable in other apps) reproduced a black screen on a UHD live channel and, separately, an app crash switching away from it (the crash did not reproduce on a follow-up capture; no native fault signal was found in that capture's logcat, so it remains unconfirmed and not yet root-caused). Initial investigation via `logcat mpv:V` found mpv's demuxer auto-probe failing -- `[lavf:v] No format found, try lowering probescore or forcing the format`, ending in `finished playback, unrecognized file format (reason 4)` -- and, since no native mpv backend set any demuxer probe-budget options, `demuxer-lavf-analyzeduration`/`demuxer-lavf-probesize` were widened for live sources on all six backends (Android, Windows, Linux, macOS, iOS, tvOS: `10`s/`10000000` bytes when live vs. `5`/`5000000`, ffmpeg's own stock defaults, otherwise). **This did not fix the black screen** -- a retest showed the same result, just after a longer stall (the wider budget giving the probe more time to keep failing, not succeeding). The probe-budget change is kept regardless: it's a harmless, correct hardening (a no-op for non-live playback, matching ffmpeg's own defaults) and a real gap worth having closed, it just wasn't this bug. Chasing the actual cause required tracing the full request chain: `curl`/`ffprobe` against the exact stream URL showed the m3u-editor `XtreamStreamController` correctly 302-redirecting to the internal `m3u-proxy` service (`M3uProxyApiController::channel` -> `M3uProxyService::getChannelUrl`, an opaque per-stream hash, not session/cookie-gated despite Laravel's default `web` middleware stamping an unrelated session cookie onto the response), but the redirected request returned zero bytes. The `m3u-proxy` (Python/FastAPI) container's own logs for that stream hash showed the real cause: `HTTPStatusError: Server error '503 Service Temporarily Unavailable'` from the upstream provider, retried 3 times with backoff, then given up -- `m3u-proxy`'s retry/backoff behavior itself worked correctly; the provider simply would not serve this UHD stream at request time. This is unrelated to Gluetun (the VPN hop earlier suspected, and to the `m3u-proxy` proxying logic, the client demuxer, or HDR) -- it is the upstream IPTV provider rejecting connections to this specific UHD channel, most likely a provider-side concurrent-connection cap on their UHD/4K tier or that feed being temporarily down. FHD channels are unaffected because they resolve to different upstream endpoints on the provider's side, not because of any client- or proxy-side format/bitrate handling difference. Not yet confirmed: whether this 503 is specific to this one channel, this playlist's UHD tier broadly, or correlates with the Gluetun egress IP (worth testing the same channel with the VPN out of the path); that's a provider-account/upstream question, not an app or m3u-proxy code fix. **Fixed on the app side:** upstream failures like this used to reach the user as either total silence (black screen, no message) or, once every native/server-transcode fallback was exhausted, mpv's raw internal string ("unrecognized file format") verbatim in the `Playback error` screen -- neither says "this isn't your app or your network." `PlaybackOrchestrator._tryLoadBackend` (`lib/playback/playback_orchestrator.dart`) now detects this failure shape via `looksLikeStreamProbeFailure` (`lib/playback/stream_probe_failure.dart`, matching mpv's own "no format found"/"unrecognized"/"invalid data found" phrasing, which is what a proxy-swallowed 5xx looks like from mpv's side since it never sees the original HTTP status) and, for live sources only, retries the same backend up to twice with a 3s delay before falling through to the next backend/transcode fallback, emitting an interim `stream_unavailable_retrying` error the UI shows as "Stream unavailable. Retrying…" in place of the loading spinner's static text (`PlayerScreen._handleError`/the loading-indicator `Text` in `lib/features/player/player_screen.dart`). If retries exhaust, the final error message is replaced with a clear, non-technical one ("This channel's stream is currently unavailable from your provider...") instead of mpv's raw text. This detection only works if the native error message actually contains mpv's diagnostic text -- true on Apple (`mpv_error_string()`) and Windows/Linux (`last_log_message` appended) already, but Android's `EndFileReason` enum carries no detail at all, so `MpvPlayerCore.kt` was also changed to subscribe to `MpvPlayer.logFlow` and append the last log line to the emitted error message (mirroring the desktop C++ cores' own pattern), otherwise Android could never match this detection. Verified: `flutter analyze`/`flutter test` pass (109 tests in `test/playback/`, including the pre-existing orchestrator and player-screen suites); Android's `MpvPlayerCore.kt` change compiles via `./gradlew :app:compileDebugKotlin`. Not yet verified: whether this actually improves the on-device experience for a real provider 503 -- that needs the same real-hardware retest as everything else above.
- Windows playback now attempts a GPU path before falling back to the existing SW pixel-buffer texture path: mpv embeds into a native child window via its `wid` option (`windows/runner/desktop_libmpv_backend.cpp`'s `CreateGpuVideoWindow`) and presents its own D3D11 swap chain directly, adapted from the open-source Plezy player's equivalent design (`edde746/plezy`, GPL-3.0). **Open architectural risk, not just an unverified implementation detail:** Plezy's own code comments say this only composites correctly (video behind the Flutter-drawn UI, so player controls stay visible) because their engine build presents Flutter's UI on a topmost DirectComposition visual explicitly ordered above the video window -- a modification to the Flutter engine itself that this project does not have and cannot build here. Flutter's own `platform_view` example ships a Windows target that renders only placeholder text, confirming the stock engine has no platform-view API to lean on instead. On stock Flutter, a plain child window's content is not guaranteed to paint behind what its parent draws in the same region -- ordinary Win32 z-order rules put a child's paint *above* its parent's. Concretely, this may mean video renders on top of player controls rather than behind them, not just "no HDR" or "black screen." Also new: `windows/runner/mpv/display_mode_manager.cpp/h` switches the OS display into HDR mode and matches the display refresh rate to the source's frame rate (at the current resolution only -- no resolution changes are ever attempted) when a GPU-path source is HDR, restoring both on stop/dispose, with a registry-persisted single-record crash-recovery journal (deliberately simplified from Plezy's dual-slot design -- see the header comment in `display_mode_manager.h`) that reapplies the saved original at next launch if a previous run crashed mid-change. This project's own environment has no Windows toolchain at all; the video window, GPU/HDR path, refresh-rate switching, and crash recovery have all now been built and exercised on real Windows hardware, surfacing (and fixing) real bugs a blind implementation pass could not have caught: a 1x1 video window causing every file to fail, a test-suite region collision, and mpv resolving the wrong `libmpv-2.dll` at runtime -- twice. First attempt: the native backend's loader was picking up the `media_kit_libs_windows_video` plugin's bundled build (kept for the MediaKit fallback adapter) ahead of any dedicated build, and that build cannot open a windowed `gpu-next`/D3D11 VO, failing with "Error opening/initializing the selected video_out (--vo) device". Fixed by fetching our own build via CMake `FetchContent` (`windows/CMakeLists.txt`, the same sourceforge `mpv-player-windows` build and version pin the open-source Plezy player fetches) and copying it into the runner output directory as `libmpv-2.dll`, which the loader already tried first -- this was believed sufficient because media_kit's bundled DLL was assumed to be named `mpv-2.dll`. It is not: media_kit_libs_windows_video's own `windows/CMakeLists.txt` names its bundled build `libmpv-2.dll` too (`media_kit_libs_windows_video_bundled_libraries`), so both copies targeted the identical filename in the identical directory, and the fetch fix did nothing to prevent a collision -- it just meant whichever copy step ran later would win. Because `CMAKE_VS_INCLUDE_INSTALL_TO_DEFAULT_BUILD` makes CMake's `install()` step (which copies media_kit's bundled libraries) its own INSTALL project that Visual Studio always builds after every other target -- including the runner target's `POST_BUILD`, which is where the fetched build gets copied -- media_kit's older build always ran last and silently overwrote ours, reproducing the identical "-20"/VO-open failure on real Windows hardware even after the fetch fix. Corrected by renaming our fetched build to `libmpv-gpu-2.dll` on copy (`windows/runner/CMakeLists.txt`) -- a filename nothing else can ever produce, removing the possibility of collision regardless of build order -- and adding it as the first name the loader tries (`kMpvDllNames` in `desktop_libmpv_backend.cpp`), ahead of the `libmpv-2.dll`/`mpv-2.dll` fallbacks kept only for a manually-vendored libmpv. This two-step discovery -- the first fix looked complete and passed a full rebuild, only for a real hardware run to reveal the same symptom via a subtler, order-dependent cause -- is exactly the kind of thing only a real Windows box surfaces, which is why release, not more blind iteration here, is the fastest path to finishing this. Following this discovery, `media_kit`/`media_kit_video`/`media_kit_libs_linux`/`media_kit_libs_windows_video` were removed from this project entirely (not just left unregistered): every platform's playback registration already used only native mpv or the platform's own player as fallback (ExoPlayer on Android, AVKit on Apple), so media_kit was dead weight everywhere, not just a Windows hazard -- it just happened to be Windows where that dead weight actively broke something, twice.

**The z-ordering question is no longer open -- it is now a CONFIRMED BLOCKER.** With the DLL collision fixed, real Windows hardware surfaced two more bugs: (1) mpv's own `ytdl_hook` script failing to find an external youtube-dl/yt-dlp binary (never bundled on any platform, since this app never plays arbitrary web pages) and treating that as a hard load failure -- `libmpv end-file error -17 (ytdl_hook: youtube-dl failed: not found or not enough permissions)` -- even for a plain local-network MP4/MKV file. Fixed by explicitly setting `ytdl=no` on every native mpv backend (`windows/runner/desktop_libmpv_backend.cpp`, `linux/desktop_libmpv_backend.cc`, the three Apple `MpvPlayerCore.swift` cores); Android's Kotlin core already had this set, which is what made it Windows/Linux/Apple-only. (2) Once that was fixed and mpv's D3D11 VO opened successfully (audio plays, no VO-open error), the video area is a **black screen**, not merely "video on top of controls" as the architectural risk above speculated. This is consistent with a second, separate Windows/DXGI quirk layered on top of the z-order problem: a top-level window using a flip-model DXGI swap chain (which the stock Flutter engine does) can cause DWM to stop compositing sibling/child HWND content into the final frame at all, not just reorder it -- the child window's own D3D11 presentation happens, but never reaches the screen. This confirms the native-child-window approach cannot work on stock Flutter, full stop, not just imperfectly: the fix is the fallback design already named above -- render mpv's output into a texture via its OpenGL render API (through ANGLE, the same GL-to-D3D11 translation layer media_kit's own Windows implementation used) and feed it to a `FlutterDesktopGpuSurfaceTexture` (`kFlutterDesktopGpuSurfaceTypeD3d11Texture2D`, a real stock Flutter Windows embedder API -- verified directly against `flutter_texture_registrar.h`/`texture_registrar.h` in the Flutter engine source, not assumed), staying inside Flutter's own proven texture compositing instead of a sibling window. Note this is a different, unrelated fix from the open-source Plezy player's own solution to the same underlying problem: Plezy requires a custom-patched fork of the Flutter engine itself (`edde746/flutter-plezy`, distributed as prebuilt binaries swapped into the local Flutter SDK's engine cache before every build) that adds DirectComposition-visual ordering support Flutter does not expose publicly. This project deliberately does not follow that path -- maintaining a Flutter engine fork across every SDK version bump is a standing engineering commitment with no existing infrastructure here, whereas the texture-based approach stays entirely within normal native-plugin territory using a real, stock, public Flutter API. That rewrite has not been implemented yet. Given that scope, the GPU child-window path was disabled at compile time (`kGpuWindowPathEnabled = false` in `desktop_libmpv_backend.cpp`'s `Load()`) rather than left in a state that silently produces a black screen; every load now goes through the SW pixel-buffer path instead, the same one this project used before GPU/HDR work began.

**Separately, resuming/continue-watching VOD playback was broken on real Windows hardware** (start-from-beginning worked; resuming from a saved position failed every time with a generic "mpv loadfile command failed") -- and turned out to be a real, longstanding bug in mpv's `loadfile` command construction, present identically in both C++ desktop backends (`windows/runner/desktop_libmpv_backend.cpp`, `linux/desktop_libmpv_backend.cc`). mpv's `loadfile` signature is `loadfile <url> [<flags> [<index> [<options>]]]` -- both files built `{"loadfile", url, "replace", "start=90.5", nullptr}`, putting the options string in the *third* positional slot (`<index>`, which mpv expects as an integer playlist-insert position), not the fourth (`<options>`). Some mpv builds tolerate this; whichever one Windows just started fetching does not. The three Apple `MpvPlayerCore.swift` cores and the Android Kotlin core already had this right (`["loadfile", uri, "replace", "0", "start=..."]`, an explicit `"0"` index before the options string) -- this was purely a gap in the two C++ desktop backends, carried over from before this session, not something introduced by this session's other fixes. Fixed by setting `start` via mpv's `set` command (Linux) or as a normal pre-`mpv_initialize` option (Windows, matching how every other option in that function is already set) instead of relying on `loadfile`'s options slot at all, on both platforms.

**Windows GPU-texture rendering rewrite (ANGLE + `FlutterDesktopGpuSurfaceTexture`), confirmed working on real Windows hardware.** With the SW pixel-buffer path proven working (Live TV, VOD from start, VOD resume all confirmed on real Windows hardware), this project implemented the real fix for the native-child-window GPU path's confirmed DWM/flip-model dead end (see above): rendering mpv's output into a D3D11 texture via ANGLE and handing it to Flutter through the real, public `FlutterDesktopGpuSurfaceTexture` embedder API, instead of a sibling window. New files: `windows/runner/angle_surface_manager.h/.cc` (the ANGLE/EGL/D3D11 interop layer -- creates its own D3D11 device and two shared textures, one mpv/ANGLE draws into and one Flutter reads from, copied via `ID3D11DeviceContext::CopyResource` right before Flutter opens the shared handle, to avoid any need to synchronize GL rendering against Flutter's raster thread). `TryLoadGpuTexture` in `desktop_libmpv_backend.cpp` hand-declares mpv's OpenGL render API structs (`mpv_opengl_init_params`, `mpv_opengl_fbo`, `MPV_RENDER_PARAM_OPENGL_INIT_PARAMS`/`_FBO`) the same way the SW path's structs are already hand-declared (this project dlopens libmpv rather than linking `mpv/render.h`), creates an `mpv_render_context` with `MPV_RENDER_API_TYPE_OPENGL` and `get_proc_address = eglGetProcAddress`, and registers a `flutter::GpuSurfaceTexture(kFlutterDesktopGpuSurfaceTypeDxgiSharedHandle, ...)` whose callback renders into the ANGLE surface's FBO 0 and copies it to the published texture before returning -- the same lazy, pull-based-on-raster-thread pattern the existing SW path already uses (`CopyPixels`), just producing a GPU texture descriptor instead of a CPU pixel buffer. `kFlutterDesktopGpuSurfaceTypeDxgiSharedHandle` was chosen deliberately over `kFlutterDesktopGpuSurfaceTypeD3d11Texture2D`: Flutter's own internal ANGLE/D3D11 device (`egl::Manager::GetDevice`) is not reachable through the public embedder API this app links against, ruling out same-device texture sharing -- the shared-handle variant lets the texture be created on any device (this app's own ANGLE-owned one) and opened independently by Flutter's engine.

Ported closely from the (fully removed from this project, see above) `media_kit_video` package's own Windows implementation (`angle_surface_manager.{h,cc}`, `video_output.cc`) -- its C++ source remained on disk in the local pub cache even after the package was removed from `pubspec.yaml`, giving a concrete, previously-shipping reference implementation to adapt rather than a blind reimplementation from ANGLE/EGL API documentation alone. Key adaptations rather than a verbatim port: this project builds with exceptions disabled (`_HAS_EXCEPTIONS=0`), so the reference's `throw std::runtime_error(...)` failure signaling was replaced with an `IsValid()`/bool-return pattern consistent with the rest of this file; dynamic texture resizing was dropped entirely in favor of the same fixed-size (`kTextureWidth`/`kTextureHeight`) approach the SW path already uses, since no other backend in this project has resize plumbing either; and the local mpv option-setting handle is named `gpu_handle` rather than `handle` specifically to keep this function's option calls textually distinct from the SW path's identical-looking ones, for the same reason the (also disabled) native-window path already does this -- this file's own architectural tests scan for exact single occurrences of some option strings.

`TryLoadGpuTexture` performs a genuine runtime capability check, not just a compile-time flag: if `ANGLESurfaceManager` fails to initialize (no suitable GPU/driver, missing ANGLE EGL extension, etc.) or mpv rejects `MPV_RENDER_API_TYPE_OPENGL` outright, nothing has been committed yet (no mpv handle left dangling) and `Load()` falls through to the proven SW path on a fresh handle automatically -- no user-visible failure, no rebuild required, unlike the compile-time-only kill switch the native-window path relies on. A compile-time kill switch (`kGpuTexturePathEnabled`) still exists as a backstop in case the runtime-fallback logic itself has a bug. ANGLE's runtime DLLs (`libEGL.dll`, `libGLESv2.dll`, `d3dcompiler_47.dll`, `zlib.dll`) are now fetched (`windows/CMakeLists.txt`) and bundled next to the executable (`windows/runner/CMakeLists.txt`'s `POST_BUILD` step) the same way `libmpv-gpu-2.dll` already is; ANGLE's own bundled SwiftShader software-Vulkan fallback (`vk_swiftshader.dll`, `vulkan-1.dll`) is deliberately not bundled, since this project already has its own proven SW pixel-buffer fallback for GPU-less machines and would never reach ANGLE's own software path.

**Confirmed on real Windows hardware over VNC on the first real-hardware pass**: Live TV and VOD both play correctly on the new GPU-texture path, with a dramatic, immediately-noticeable latency improvement over the SW pixel-buffer path -- consistent with the ANGLE/D3D11 texture route actually eliminating the CPU-side render-copy-upload round trip the SW path required every frame. This project's own environment still has no Windows toolchain at all, so this result came entirely from the user's own hardware test, the same verification path every other Windows GPU/HDR fix in this document has relied on. Not yet separately verified: HDR toggle behavior against an actual HDR10 source/display (GPU rendering working does not by itself confirm the HDR metadata/OS-display-switch path is correct), and the runtime ANGLE/D3D11-unavailable fallback-to-SW path (not exercised, since ANGLE initialized successfully on the hardware tested).

A related, still-open gap surfaced by this same investigation: Windows/Linux desktop has no server-transcode fallback adapter registered at all (`buildPlaybackOrchestrator()` in `app_router.dart` registers only `desktopLibmpv`/`macMpvNative` for desktop), so any mpv load failure on desktop -- VOD resume or otherwise -- is currently a dead end with no automatic recovery, unlike Android/Apple's ExoPlayer/AVKit fallbacks. Also fixed in the same pass: `PlayerScreen._openAndSeek` (`lib/features/player/player_screen.dart`) called `orchestrator.seek()` immediately after `open()` regardless of whether `open()` actually left an active adapter behind; on a non-recoverable failure this threw a second, unrelated `StateError` ("PlaybackOrchestrator has no active backend") that overwrote the real error message already surfaced through the proper error stream, which is what actually made this bug hard to diagnose from the UI alone.

Verified here: `flutter build macos` and `flutter build ios --simulator` both pass cleanly; the tvOS project's three modified Swift files (`MpvPlayerCore.swift`, `MpvPlayerPlugin.swift`, `MpvPlayerPlatformView.swift`) compile without error via `xcodebuild -destination "generic/platform=tvOS"` (a full app link is blocked by an unrelated, pre-existing `sqflite_tvos` CocoaPods/SPM plugin-registration mismatch in this environment, confirmed unrelated to this change by isolating the compile step). Not verified here, same as every other HDR fix in this document: actual HDMI mode-switch behavior on a real Apple TV connected to an HDR display, and actual EDR engagement on real iOS/macOS hardware with HDR content -- this project has no such hardware to self-verify against.
