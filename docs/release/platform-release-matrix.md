# Platform Release Matrix

This document is the production release source of truth for the Flutter client. It records the toolchain baseline, signing placeholders, and current blockers without claiming platform builds pass before the matching SDKs and native dependencies are present. Blocking release targets: Linux desktop, Windows desktop, Android phone/tablet, and Android TV. macOS, iOS, iPadOS, and tvOS are non-blocking gated tracks for this Desktop+Android release.

## Active CI Baseline

The CI gate workflow is `.github/workflows/ci.yml`. It runs these Flutter gates from `flutter_client/` with the pinned Flutter binary:

```bash
/tmp/flutter/bin/flutter analyze
/tmp/flutter/bin/flutter test
```

The release publication workflow is `.github/workflows/release.yml`. It builds and publishes artifacts for all platforms (Android, Linux, Windows, iOS, tvOS, macOS) with separate non-Apple and Apple release tracks.

The workflow does not run Electron builder commands, Electron scripts, or React Native/Expo release jobs. The React Native/Expo app has been fully removed; only the Flutter client remains in this repository.

## Honest Release Blockers

- Android SDK/JDK setup, signed release artifacts, Play Console metadata, physical Android phone/tablet QA, and physical Android TV hardware validation are not completed by this baseline task. Emulator logs are supplemental only.
- Android now uses native mpv (`PlaybackBackend.androidMpv`, `dev.jdtech.mpv` libmpv bindings, rendered via a `SurfaceView`-hosted `AndroidView`) as the primary playback path, with Media3/ExoPlayer as the automatic fallback and m3u-editor server transcode as the final fallback. Native mpv playback has only been confirmed via limited manual testing on physical Android TV hardware (playback starts, video renders, back-navigation tears down cleanly); subtitle rendering, HDR, and broader device/codec QA remain open before this can be claimed release-ready.
- Windows playback now attempts a GPU path before falling back to the existing SW pixel-buffer texture path: mpv embeds into a native child window via its `wid` option (`windows/runner/desktop_libmpv_backend.cpp`'s `CreateGpuVideoWindow`) and presents its own D3D11 swap chain directly, adapted from the open-source Plezy player's equivalent design (`edde746/plezy`, GPL-3.0). **Open architectural risk, not just an unverified implementation detail:** Plezy's own code comments say this only composites correctly (video behind the Flutter-drawn UI, so player controls stay visible) because their engine build presents Flutter's UI on a topmost DirectComposition visual explicitly ordered above the video window -- a modification to the Flutter engine itself that this project does not have and cannot build here. Flutter's own `platform_view` example ships a Windows target that renders only placeholder text, confirming the stock engine has no platform-view API to lean on instead. On stock Flutter, a plain child window's content is not guaranteed to paint behind what its parent draws in the same region -- ordinary Win32 z-order rules put a child's paint *above* its parent's. Concretely, this may mean video renders on top of player controls rather than behind them, not just "no HDR" or "black screen." Also new: `windows/runner/mpv/display_mode_manager.cpp/h` switches the OS display into HDR mode and matches the display refresh rate to the source's frame rate (at the current resolution only -- no resolution changes are ever attempted) when a GPU-path source is HDR, restoring both on stop/dispose, with a registry-persisted single-record crash-recovery journal (deliberately simplified from Plezy's dual-slot design -- see the header comment in `display_mode_manager.h`) that reapplies the saved original at next launch if a previous run crashed mid-change. This project's own environment has no Windows toolchain at all; the video window, GPU/HDR path, refresh-rate switching, and crash recovery have all now been built and exercised on real Windows hardware, surfacing (and fixing) real bugs a blind implementation pass could not have caught: a 1x1 video window causing every file to fail, a test-suite region collision, and mpv resolving the wrong `libmpv-2.dll` at runtime -- twice. First attempt: the native backend's loader was picking up the `media_kit_libs_windows_video` plugin's bundled build (kept for the MediaKit fallback adapter) ahead of any dedicated build, and that build cannot open a windowed `gpu-next`/D3D11 VO, failing with "Error opening/initializing the selected video_out (--vo) device". Fixed by fetching our own build via CMake `FetchContent` (`windows/CMakeLists.txt`, the same sourceforge `mpv-player-windows` build and version pin the open-source Plezy player fetches) and copying it into the runner output directory as `libmpv-2.dll`, which the loader already tried first -- this was believed sufficient because media_kit's bundled DLL was assumed to be named `mpv-2.dll`. It is not: media_kit_libs_windows_video's own `windows/CMakeLists.txt` names its bundled build `libmpv-2.dll` too (`media_kit_libs_windows_video_bundled_libraries`), so both copies targeted the identical filename in the identical directory, and the fetch fix did nothing to prevent a collision -- it just meant whichever copy step ran later would win. Because `CMAKE_VS_INCLUDE_INSTALL_TO_DEFAULT_BUILD` makes CMake's `install()` step (which copies media_kit's bundled libraries) its own INSTALL project that Visual Studio always builds after every other target -- including the runner target's `POST_BUILD`, which is where the fetched build gets copied -- media_kit's older build always ran last and silently overwrote ours, reproducing the identical "-20"/VO-open failure on real Windows hardware even after the fetch fix. Corrected by renaming our fetched build to `libmpv-gpu-2.dll` on copy (`windows/runner/CMakeLists.txt`) -- a filename nothing else can ever produce, removing the possibility of collision regardless of build order -- and adding it as the first name the loader tries (`kMpvDllNames` in `desktop_libmpv_backend.cpp`), ahead of the `libmpv-2.dll`/`mpv-2.dll` fallbacks kept only for a manually-vendored libmpv. This two-step discovery -- the first fix looked complete and passed a full rebuild, only for a real hardware run to reveal the same symptom via a subtler, order-dependent cause -- is exactly the kind of thing only a real Windows box surfaces, which is why release, not more blind iteration here, is the fastest path to finishing this. Following this discovery, `media_kit`/`media_kit_video`/`media_kit_libs_linux`/`media_kit_libs_windows_video` were removed from this project entirely (not just left unregistered): every platform's playback registration already used only native mpv or the platform's own player as fallback (ExoPlayer on Android, AVKit on Apple), so media_kit was dead weight everywhere, not just a Windows hazard -- it just happened to be Windows where that dead weight actively broke something, twice.

**The z-ordering question is no longer open -- it is now a CONFIRMED BLOCKER.** With the DLL collision fixed, real Windows hardware surfaced two more bugs: (1) mpv's own `ytdl_hook` script failing to find an external youtube-dl/yt-dlp binary (never bundled on any platform, since this app never plays arbitrary web pages) and treating that as a hard load failure -- `libmpv end-file error -17 (ytdl_hook: youtube-dl failed: not found or not enough permissions)` -- even for a plain local-network MP4/MKV file. Fixed by explicitly setting `ytdl=no` on every native mpv backend (`windows/runner/desktop_libmpv_backend.cpp`, `linux/desktop_libmpv_backend.cc`, the three Apple `MpvPlayerCore.swift` cores); Android's Kotlin core already had this set, which is what made it Windows/Linux/Apple-only. (2) Once that was fixed and mpv's D3D11 VO opened successfully (audio plays, no VO-open error), the video area is a **black screen**, not merely "video on top of controls" as the architectural risk above speculated. This is consistent with a second, separate Windows/DXGI quirk layered on top of the z-order problem: a top-level window using a flip-model DXGI swap chain (which the stock Flutter engine does) can cause DWM to stop compositing sibling/child HWND content into the final frame at all, not just reorder it -- the child window's own D3D11 presentation happens, but never reaches the screen. This confirms the native-child-window approach cannot work on stock Flutter, full stop, not just imperfectly: the fix is the fallback design already named above -- render mpv's output into a texture via its OpenGL render API (through ANGLE, the same GL-to-D3D11 translation layer media_kit's own Windows implementation used) and feed it to a `FlutterDesktopGpuSurfaceTexture` (`kFlutterDesktopGpuSurfaceTypeD3d11Texture2D`, a real stock Flutter Windows embedder API -- verified directly against `flutter_texture_registrar.h`/`texture_registrar.h` in the Flutter engine source, not assumed), staying inside Flutter's own proven texture compositing instead of a sibling window. Note this is a different, unrelated fix from the open-source Plezy player's own solution to the same underlying problem: Plezy requires a custom-patched fork of the Flutter engine itself (`edde746/flutter-plezy`, distributed as prebuilt binaries swapped into the local Flutter SDK's engine cache before every build) that adds DirectComposition-visual ordering support Flutter does not expose publicly. This project deliberately does not follow that path -- maintaining a Flutter engine fork across every SDK version bump is a standing engineering commitment with no existing infrastructure here, whereas the texture-based approach stays entirely within normal native-plugin territory using a real, stock, public Flutter API. That rewrite has not been implemented yet.
- Linux production packaging must bundle `libmpv.so.2`, verify dynamic dependencies and ZIP integrity, and include license notices before public release.
- Linux Wayland sessions use a GPU-rendered video plane (`linux/wayland_video_surface.h/.cc`, a `wl_subsurface` stacked below the Flutter window driven by mpv's OpenGL render API through its own isolated EGL context -- Flutter's Linux embedder has no platform-view API and its `FlTextureGL` is hardcoded to 8-bit RGBA, so this is the only route to GPU-accelerated rendering there) before falling back to the original software pixel-buffer texture path. This was built and click-tested on real Wayland hardware over a VNC session (playback, scrubbing, and multiview all confirmed working; `M3U_TV_SHOW_PLAYBACK_DIAGNOSTICS=true` confirms the "Desktop libmpv" backend is active). Two CMake build issues found on that hardware (`PkgConfig::WAYLAND_CLIENT` target not found; a required `IMPORTED_TARGET` keyword missing on the Wayland `pkg_check_modules` calls) have been fixed.
- The GPU video plane now additionally attempts HDR passthrough via Wayland's `wp_color_manager_v1` (`color-management-v1`) protocol (`linux/hdr_metadata.h`, `linux/wayland/color-management-v1-client-protocol.h/.c` vendored from upstream wayland-protocols, and the color-management additions to `linux/wayland_video_surface.h/.cc`): a two-phase image-description transition (stage and validate against the compositor, switch mpv's output color space once it settles, then commit and present atomically), ported closely from the open-source Plezy player's equivalent implementation (`edde746/plezy`, GPL-3.0) as a reference, with its async multi-request toggle-queue/generation-counter machinery deliberately left out -- this app applies HDR automatically per source rather than exposing a user toggle, so a single serialized transition per `video-params` change is equivalent and far simpler. One CMake build issue found on real hardware (`CMAKE_C_COMPILE_OBJECT` not set -- the vendored protocol file is plain C, and `project()` only declared the `CXX` language) has been fixed (`project(runner LANGUAGES CXX C)`); the build now succeeds and click-testing confirmed playback still works with the HDR code paths compiled in. The HDR passthrough behavior itself (an actual HDR file, an HDR-capable display switched into HDR, a compositor implementing `color-management-v1` such as KWin 6.4+) has not yet been exercised in this project's own testing, but the design and protocol usage follow Plezy's shipping implementation closely -- this project does not have the range of HDR displays and compositors needed to self-verify further, and getting that coverage is exactly what shipping this to users on their own hardware is for. X11 sessions are unaffected either way (no GPU path, no HDR).
- Windows production packaging must verify `libmpv-gpu-2.dll` and required runtime files inside the ZIP. Authenticode or MSIX signing and real-device playback evidence remain release blockers.
- Apple/tvOS gates do not block the Desktop+Android release track. Apple work is a non-blocking gated track while Linux desktop, Windows desktop, Android phone/tablet, and Android TV remain the blocking release targets.
- macOS and iOS/iPadOS require Xcode host evidence, provisioning/codesigning, and notarization or App Store review preparation before any Apple release claim. Native mpv (MPVKit) playback itself is confirmed working on both platforms; what remains is submission/signing evidence, not the playback backend.
- MPVKit/libmpv is now the primary shipping playback backend on iOS/tvOS/macOS: the project's GPL-3.0 relicense removed the prior App Store/GPL incompatibility. A dedicated legal/App Store review pass on GPL-3.0 binary distribution obligations (source offers, review guideline 2.5.1) has not yet been done and should happen before submission. macOS Multiview now runs on native mpv (`MacMpvNativeBackend`) instead of media_kit; not yet click-tested on real hardware (see the macOS desktop row above).
- tvOS build and playback both work via a manually-wired Xcode project; remaining gaps before a production claim are missing tvOS plugin implementation audit, Platform.isIOS vs tvOS platform detection risks, and community/custom-embedder-equivalent proof for store submission. The overlay-scaling cosmetic bug has been fixed.
- No signing keys, store credentials, private stream URLs, or provider credentials are stored in this repository.


## Android App ID, Signing, and TV Release Metadata

- Application ID: `dev.sparkison.tv`; active Android release configuration must not use `com.example` or other template identifiers.
- `flutter_client/android/app/build.gradle.kts` reads `ANDROID_KEYSTORE_PATH`, `ANDROID_KEY_ALIAS`, `ANDROID_KEYSTORE_PASSWORD`, and `ANDROID_KEY_PASSWORD` from Gradle properties, environment variables, or the local ignored file `flutter_client/android/signing.properties`.
- The publication workflow enables `ANDROID_REQUIRE_RELEASE_SIGNING`. Missing signing values or a missing keystore path therefore fail publication instead of producing a debug-signed artifact. The workflow verifies the APK signer before staging and records its SHA-256 certificate digest in the job summary.
- Without `ANDROID_REQUIRE_RELEASE_SIGNING`, contributors can create a debug-signed release build for local development only and must not publish it.
- Users upgrading from a debug-signed version must uninstall the existing debug-signed app once before installing the first stable release-signed build. Uninstalling removes local app data and settings, so users must configure the app again afterward.
- Android TV launcher metadata must remain present in `flutter_client/android/app/src/main/AndroidManifest.xml`: `android.software.leanback`, optional touchscreen support, application banner, exported main activity, and `LEANBACK_LAUNCHER` category.
- Play Store and Android TV store distribution remain blocked until signed AAB/APK artifacts, Play Console metadata, data-safety declarations, codec/legal review, physical Android phone/tablet QA, and physical Android TV hardware QA are supplied as release evidence outside git.

## Dependency and License Gates

- Media3/ExoPlayer is the Android playback dependency path for this release and must keep its AndroidX license notices with generated or bundled notices for distributed artifacts.
- Flutter plugins and Flutter SDK notices must be included in each store or sideload artifact through the platform's generated license notice mechanism or an equivalent third-party notices file.
- mpv/libmpv, FFmpeg, MPVKit, and libass are desktop/native playback dependencies only where explicitly implemented and packaged. Their LGPL/GPL build flags, dynamic/static linking choices, source-offer obligations, App Store policy impact, native dependency review, and attribution notices must be reviewed before public distribution.
- GPL policy: do not ship GPL-only binaries, GPL-derived code, or Plezy reference code in a store/direct-download artifact unless the release owner explicitly accepts the GPL distribution obligations and records that decision in release evidence.
- License notices are a release gate. No Play Store, App Store, Microsoft Store, sideload, or direct-download release is complete until dependency/license notices and codec redistribution obligations are reviewed and saved with the signed artifact evidence.
